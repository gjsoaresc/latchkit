# Requirement-change workflow comparison

Source-linked comparison matrix for issue [#116](https://github.com/willahealm/latchkit/issues/116) acceptance criterion 5. All four tools below were reviewed on **6 September 2026** and versions/dates are pinned as of that date; capability descriptions can change, so recheck before publishing an external comparison. This is a documentation comparison, matching the [#109 epic](https://github.com/willahealm/latchkit/issues/109)'s own research basis. **It is not a head-to-head measured result** — no permitted, comparable observed run of Pilot Shell, OpenSpec, Spec Kit, or TinySpec has been performed. A competitive or "wins on X" claim requires such a run, not this table.

No proprietary Pilot Shell material — code, prompts, documentation text, or visual assets — is reproduced here or required to run Latchkit's [requirement-change demo](requirement-change-demo.md). Everything below is an original summary of publicly documented behavior, cited to its source.

## Adaptive/review features and lightweight tradeoffs, fairly stated

- **Pilot Shell** invests the most in an integrated runtime (adaptive execution, independent judging, a Console UI, hooks) but is proprietary and not redistributable; using it as a baseline for a real comparison would require it to run independently of Latchkit, which this repository does not require to run its own demo.
- **OpenSpec** makes a deliberate, argued choice to keep its update mechanism lightweight (no dependency graph, no staleness ledger) for v1, explicitly because the artifacts are small enough that an agent already has to re-read them. That is a real, considered lightweight tradeoff, not an oversight — and it is also explicitly scoped away from the cross-change reconciliation problem Latchkit's #110-#112 slice targets.
- **Spec Kit** does not pick one persistence model for the user; it documents three with stated tradeoffs and leaves the choice to the team. Latchkit's baseline/reconciliation split is closer in spirit to "flow-back" today (manual reconciliation) and aims to reduce the silent-divergence risk Spec Kit itself names for that model.
- **TinySpec** is the lightest-ceremony option reviewed: no formal review/approval workflow is documented at all, which is a legitimate design choice for its target use case, not a gap to be scored against automatically — a "more machinery" comparison would be unfair to what TinySpec is trying to be.

## What would turn this into a measured comparison

A head-to-head measured claim requires a permitted, comparable observed run of the same scenario across tools (same starting tree, same requirement text, same change timing, same acceptance checks), reported with the same honesty requirements as [the requirement-change evaluations](requirement-change-evaluations.md): full denominator, failures, uncertainty, and no invented percentage savings. No such run exists yet for any of the four tools above; running one is out of scope for this increment.
