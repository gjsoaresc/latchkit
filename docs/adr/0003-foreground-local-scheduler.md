# ADR 0003: Foreground local scheduler

Schedules are an optional project-local JSON record under `.latchkit/schedules/`. They run only while `latchkit schedule start` remains in the foreground; Latchkit does not install a Windows Task Scheduler job, launch daemon, cron entry, launchd agent, service, or WSL bridge.

Each schedule stores its IANA timezone, fixed-minute recurrence, next absolute instant, canonical target project, provider, instructions, explicit authorization scope/reference, host-local authorization flag, output and timeout limits, skip-overlap policy, skip-missed-run policy, and bounded run result metadata. The foreground process creates a durable task for each authorized attempt and invokes the existing task controller, adapters, and owned process runner. Scope and provenance are included in that task and prompt; the provider retains its effective tool permissions. A prose scope is not a filesystem sandbox. No permission bypass flags or credentials are added.

One foreground owner is allowed per canonical project. It holds the existing challenge-response task lock for its full lifetime, in the dedicated `.latchkit/schedules/owner/` namespace. A second owner cannot recover or erase live work. Malformed, ambiguous, or foreign-host ownership is refused; a stale endpoint is never used to signal a persisted PID. The owner runs at most one schedule at a time and releases its lock only after owned processes settle. State reads and writes refuse managed-directory junctions/symlinks and relocated project targets.

On startup, a formerly running record becomes `interrupted` and its schedule is disabled. The linked task and session remain inspectable. The process may have left an orphan child, so automatic resume is refused: inspect the existing task/process evidence and create a new explicit schedule only after resolving the old attempt. Recovery does not claim that a stale scheduler lock proves all descendants exited. Clean pause/resume preserves history and resets the next instant; edit/remove refuse active runs. Removing a stopped schedule leaves its durable task evidence intact.

Past due times move to the next interval without catch-up on startup. During operation a full missed interval is skipped, while ordinary polling lateness can start one due attempt. Fixed-minute recurrence uses absolute instants, so DST and clock rollback do not create duplicate local-wall-clock runs; the IANA timezone is display metadata, not a wall-clock cron expression. Recurrences range from one minute to one week. State is bounded to 100 schedules and 4 MiB, with at most 100 history entries per schedule, 24-hour timeouts, and 16 MiB of provider output per attempt. `--max-runs` controls retained schedule history, not an inference budget; durable task evidence is retained independently.

A missing explicit host-local authorization produces one persisted `blocked` run, disables the schedule, and never starts a provider command. Editing an execution definition invalidates its prior authorization unless the edit includes new scope, reference, and explicit authorization. A provider refusal or unverified session also disables its schedule. Exit code zero cannot verify delivery: the linked task's acceptance evidence remains authoritative, and this first slice stops as `blocked` until that evidence is verified through the existing workflow. Ordinary blocked wakeups produce no repetitive attempts. Task state exposes the existing local event history; a dedicated scheduler notification UI is deferred.

The persisted authorization digest binds the provider, instructions, target, recurrence, scope/provenance, authorization flag, and resource limits. It detects out-of-band definition edits; it is not an authentication signature and cannot defend against a user who can rewrite both the definition and digest. Schedule creation and editing remain explicit local actions, and provider permissions remain authoritative.

`schedule cancel` records a durable request. The owning foreground process checks it every 100 ms and aborts only its captured child through the process runner; the command never kills a PID read from disk. A cancellation remains pending until that owner settles, and late success cannot overwrite cancellation. Foreground shutdown drains cancellation before releasing ownership. Timeout and output limits apply to both model-free probes and inference launches without changing provider approval policy.

Native Windows smoke uses PowerShell with a project path containing spaces and no administrator rights: `latchkit schedule create --project "C:\work\my project" --provider codex --prompt "Inspect current diagnostics" --scope "Read project diagnostics" --reference "Explicit local test" --every-minutes 1`, followed by `latchkit schedule start --project "C:\work\my project"`. Without `--host-local-authorized`, inspect the one blocked record and verify that no provider starts. In another terminal exercise `schedule inspect`, `pause`, `edit`, `resume`, `cancel`, and `export`, each with `--project` and the schedule `--id` where applicable. Add explicit host-local authorization only when a real provider run is intended and authorized.

Linux/macOS use the same foreground commands with a native path containing spaces. WSL is a separate Linux process and must use its own native project/state; copying or sharing a Windows schedule target is refused. It cannot adopt or cancel Windows ownership. These non-Windows procedures have not been executed in this change. Credential-free native Windows tests exercise actual child termination, a separate CLI cancellation process, duplicate ownership, killed-owner recovery, and directory junction refusal. They do not establish real-provider unattended approval behavior or production release qualification.

Review validation on Windows 11 x64 (`10.0.26200`): `npm ci` completed with zero reported vulnerabilities; `npm run check` passed; `npm test` passed 248 tests with three pre-existing file-symlink capability skips (251 total), using Node.js 26.8.1. The strengthened `node --test test/scheduled-work.test.js` passed all 14 tests under both Node.js 26.8.1 and Node.js 22.23.2. Four new regression tests were observed failing against the initial scheduler implementation before the safety fixes. No provider account, model session, service installation, or non-Windows qualification was involved.
